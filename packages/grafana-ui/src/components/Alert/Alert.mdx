# Alert

Alerts are used for displaying important messages or notifications to users. The user is expected only to read the message by default; any action provided is considered optional.

## When to use

Use Alerts to inform users of updates, changes, or issues. Providing users feedback, keeping them informed, and keeping disruptions to a minimum is important. There are two different use-cases for Alerts: task-generated and system-generated Alerts.

- **Task-generated** Alerts are triggered based on the behaviors of the user and provide quick, direct feedback. This type of Alert should be placed closely to the area the user is actively working in.
- **System-generated** Alerts are triggered by the system, unconnected to the actions of a user. Use these Alerts to provide explanation of system status or other events that have occurred elsewhere.

### When to use an inline alert

An inline alert appears above or below the content it relates to, and reports the status of an action or of the system. Use one:

- To inform at that time how to continue a task in which users must perform an action.
- To provide some options for users to take action.
- To explain in detail the reasons why something can't be done by users.

### When to use a toast

A toast is a short message that slides in at the top-right corner of the page. It hides itself after a few seconds, or when the user dismisses it, and doesn't interrupt the user or need an action. Use one:

- To convey general confirmation or non-critical actions.
- Immediately after an event is taken, such as a permission is updated or some Dashboards are imported or deleted.

Don't render `Alert` yourself for a toast. Publish an `appEvent` instead, and Grafana shows the toast, as in the toast example under Usage.

### Persistent and passive alerts

- **Persistent** alerts are usually urgent and need immediate attention. They stay until the user dismisses them or acts on them. Only an inline alert can be persistent.
- **Passive** alerts are informational, and report something that needs no action from the user. A toast is always passive, and an inline alert can be passive.

### Choosing a severity

- **`info`:** information that doesn't interrupt the user's current task and needs no immediate action. It is blue, with the `info-circle` icon.
- **`success`:** confirms that a task or an action completed as expected. It usually needs no further action. It is green, with the `check` icon.
- **`warning`:** a current status that users should be aware of, or that could have serious consequences, such as an undesirable action. It often stays until the user dismisses it or resolves the issue. It is yellow, with the `exclamation-triangle` icon.
- **`error`:** something failed, and the user is expected to act. Where you can, say how to fix it. It stays until the user has fixed the issue. It is red, with the `exclamation-circle` icon.

### When to use AlertBanner instead

Use `AlertBanner` for a message about the whole page or account that the user shouldn't miss, such as an overdue invoice or a usage limit that has been reached. Place it at the top of the page, and show at most one on a page.

Use `Alert` for a message about one part of the page or a task the user is doing, and place it next to the related element. Choose between them by the scope of the message, not by its severity: both take the same four severities.

## Never use for

- **Showing a toast by rendering `Alert` yourself.** Publish an `appEvent` with `getAppEvents()` instead, and Grafana shows the toast. See the toast example under Usage.
- **A message about the whole page or account that the user shouldn't miss.** Use `AlertBanner` at the top of the page. See "When to use AlertBanner instead" above.
- **Asking the user to make a decision before they continue.** Use `Modal`, or `ConfirmModal` for a simple confirmation such as deleting an item. An alert doesn't stop the user from carrying on with the page, so it can't make sure they answer.
- **A feature announcement or other promotional message.** Use `Banner`. A promotion has no severity, and showing it as an `info` alert weakens genuine info messages, which tell the user something about their stack or task.
- **A validation error on a single form field.** Use the `invalid` and `error` props on `Field`. `Field` shows the message below the input and links it to the input with `aria-describedby`.

## Do's and don'ts

### Writing content

- Do use the severity that matches the message. See "Choosing a severity" above.
- Do give every alert a title. Titles are required. Keep them concise, explicit, human-focused and jargon free, and convey the most important part of the message.
- Do keep the details short and focused on why the alert is shown. Tell users what to do next or how to fix the problem, so that they aren't blocked. Details are optional, so use them sparingly.
- Don't repeat the title in the details.
- Do use plain, simple language. Don't use jargon or raw system errors. See the [UX writing guidelines](https://grafana.com/docs/writers-toolkit/write/style-guide/ux-writing/).
- Do keep call to action labels short, a few words at most, and make clear what the user can do. Add a call to action when the user can fix the reason for the alert.
- Do show an alert when it is relevant to the user's current workflow and should be addressed now.
- Don't hide other content with inline alerts.

### Placement and links

- Do place an inline alert immediately above or below the related element.
- Only persistent notifications should contain text links or buttons. Don't add them to passive notifications.

### Actions and dismissal

A dismissible alert offers the user at most two choices:

- **Dismiss the alert.** Set `onRemove` to show a close icon button. When you need to make clearer what dismissing does, set `buttonContent` to show a text button that means the same in its place, for example "Not now" or "Hide for today". Keep it to two or three words. `buttonContent` is a text alternative to the close icon, not a second action: it calls `onRemove`, and is shown only when `onRemove` is set.
- **Take a further action.** Pass one action in `action`. The action is optional for the user: ignoring it and dismissing the alert is a valid choice, so don't make the alert depend on it.

`Alert` sets the appearance of the buttons in `action`, so that every action button in an alert looks the same. It renders a `Button` as a `BannerActionButton`, and a `LinkButton` as a `BannerActionButton` link, in the outline colors of the alert's severity. It finds them at any depth, such as inside a fragment or a layout component:

- **Ignored:** `variant`, `fill`, `size`, `fullWidth` and `className`. A `variant="primary"` or `variant="destructive"` button looks the same as any other, so don't set them.
- **Kept:** the other props, such as `onClick`, `href`, `target`, `icon`, `tooltip`, `disabled`, `type` and `ref`.

A `BannerActionButton` without a `severity` or `customColor` gets the alert's severity. Any other element is rendered as passed, with its own appearance. That includes a component that renders a `Button` itself, because `Alert` only sees the elements passed in.

`Alert` places `action` beside the message and wraps it below the message when space is narrow. The dismiss button, either the close icon or the `buttonContent` button, sits with `action` and wraps with it. Don't position your own button over the alert.

```tsx
// Don't
<Alert title="Quota limit reached" severity="warning" className={css({ position: 'relative' })}>
  You have reached your quota limit.
  <Button className={css({ position: 'absolute', top: 8, right: 8 })}>Request increase</Button>
</Alert>

// Do
<Alert
  title="Quota limit reached"
  severity="warning"
  action={<Button>Request increase</Button>}
  onRemove={onDismiss}
>
  You have reached your quota limit.
</Alert>
```

### Spacing and styling

Use `bottomSpacing` and `topSpacing` to change the space around an alert. They take theme spacing units: the defaults are `2` below and `0` above.

Don't change the alert's inner padding by selecting its inner elements with `className`, because its markup isn't part of its API. See [styling a component's internal elements](https://github.com/grafana/grafana/blob/main/packages/grafana-ui/src/guidance/patterns/styling-internals.md).

```tsx
// Don't: override the inner padding
<Alert title="Saved" severity="success" className={css({ '& > div': { padding: 0 } })} />

// Do: change only the space around the alert
<Alert title="Saved" severity="success" bottomSpacing={0} />
```

## Usage

```tsx
import { Alert } from '@grafana/ui';

<Alert title={title} severity={severity} buttonContent={buttonContent} onRemove={onRemove}>
  Child content that includes some alert details, like maybe what actually happened.
</Alert>;
```

`severity` defaults to `error`.

To show a toast, publish an `appEvent` with the right type and payload, using `AppEvents` and `getAppEvents()`. Grafana renders the toast for you, as an elevated, dismissible `Alert`.

```tsx
import { AppEvents } from '@grafana/data';
import { getAppEvents } from '@grafana/runtime';

const appEvents = getAppEvents();
appEvents.publish({
  type: AppEvents.alertSuccess.name,
  payload: [text + ': ' + resp.status + ' (' + resp.statusText + ')'],
});
```

## Accessibility

`Alert` handles:

- **Role:** `error` and `warning` alerts get `role="alert"`, and `info` and `success` alerts get `role="status"`. Pass `role` to override it.
- **Name:** the alert's accessible name is its `title`. Pass `aria-label` to override it.
- **Close button:** the close icon button has the label "Close alert".

You provide:

- A `title` that makes sense on its own, because screen readers use it to name the alert.
- The right `severity`. `role="alert"` is announced as soon as the alert appears, so keep `error` and `warning` for messages that need that attention.
