# Alert

Alert is a fundamental element used for displaying important messages or notifications to users.

## When to use

Use Alerts to inform users of updates, changes, or issues. Providing users feedback, keeping them informed, and keeping disruptions to a minimum is important. There are two different use-cases for Alerts: task-generated and system-generated Alerts.

- **Task-generated** Alerts are triggered based on the behaviors of the user and provide quick, direct feedback. This type of Alert should be placed closely to the area the user is actively working in.
- **System-generated** Alerts are triggered by the system, unconnected to the actions of a user. Use these Alerts to provide explanation of system status or other events that have occurred elsewhere.

### When to use an inline banner

- To inform at that time how to continue a task in which users must perform an action.
- To provide some options for users to take action.
- To explain in detail the reasons why something can't be done by users.

### When to use a toast

- To convey general confirmation or non-critical actions.
- Immediately after an event is taken, such as a permission is updated or some Dashboards are imported or deleted.
- Status according to use cases:
  - _Success_: When any action is successful, it is confirmed when a task is completed as expected.
  - _Warning_: It is used to report a current status that users should be aware of or that could have serious consequences.
  - _Error_: Inform users of an error, and sometimes provide more information about how to fix the error.

## Never use for

- **Showing a toast by rendering `Alert` yourself.** Publish an `appEvent` with `getAppEvents()` instead, and Grafana shows the toast. See the toast example under Usage.
- **A validation error on a single form field.** Use the `invalid` and `error` props on `Field`. `Field` shows the message below the input and links it to the input with `aria-describedby`.

## Do's and don'ts

### Writing content

- Do use the appropriate status for the message (info/success/warning/error).
- Do use plain, simple language for the messages to ensure users understand them and know how to address them.
- Do focus on notifications if they are relevant to the users' current workflow and should be addressed immediately.
- Don't use Primary calls to actions.
- Don't hide other content with inline notifications.
- Don't repeat the alert copy/title on the details message.
- Do give every alert a title. Titles are required, always, and should be concise, human-focused and jargon free so users can easily understand them.
- Do keep call to action labels concise and short (a few words at most), and make the action the user can take clear.

### Placement and links

- Do place an inline banner immediately above or below the related element.
- Only persistent notifications should contain text links or buttons. Don't add them to passive notifications.

### Actions

Pass a separate action in `action`, and dismissal in `onRemove`. `Alert` places `action` beside the message and wraps it below the message when space is narrow. If you also set `buttonContent`, the dismiss button joins `action` and wraps with it. With `onRemove` alone, the close icon sits at the alert's edge instead. Don't position your own button over the alert.

```tsx
// Don't
<Alert title="Quota limit reached" severity="warning" className={css({ position: 'relative' })}>
  You have reached your quota limit.
  <Button className={css({ position: 'absolute', top: 8, right: 8 })}>Request increase</Button>
</Alert>

// Do
<Alert
  title="Quota limit reached"
  severity="warning"
  action={<Button variant="secondary">Request increase</Button>}
  onRemove={onDismiss}
>
  You have reached your quota limit.
</Alert>
```

With `onRemove` alone, `Alert` shows a close icon button. Add `buttonContent` to replace the close icon with a secondary button that shows that content.

### Spacing and styling

Use `bottomSpacing` and `topSpacing` to change the space around an alert. They take theme spacing units: the defaults are `2` below and `0` above.

No prop controls the alert's inner padding. Don't change it by selecting the alert's inner elements with `className`, because its markup isn't part of its API. See [styling a component's internal elements](https://github.com/grafana/grafana/blob/main/packages/grafana-ui/src/guidance/patterns/styling-internals.md).

```tsx
// Don't: override the inner padding
<Alert title="Saved" severity="success" className={css({ '& > div': { padding: 0 } })} />

// Do: change only the space around the alert
<Alert title="Saved" severity="success" bottomSpacing={0} />
```

## Usage

```tsx
import { Alert } from '@grafana/ui';

<Alert title={title} severity={severity} buttonContent={buttonContent} onRemove={onRemove}>
  Child content that includes some alert details, like maybe what actually happened.
</Alert>;
```

`severity` defaults to `error`.

### Types

Within Grafana, we have two different types of alerts and they can be used depending on the context and content.

1. **Inline banner**:
   - To notify users of the status of an action. They appear at the top or bottom of the main content area
   - Passive or Persistent
2. **Toast**:
   - These temporary window elements are used to display short messages; they appear at the top-right corner of the screen and can be dismissed by clicking the [x] or it will disappear after a few seconds
   - Passive

### Behaviors

1. **Persistent**: They are usually urgent and intrusive, require immediate attention and require action to be dismissed.
2. **Passive**: Are informational, report a system issue that does not require any action by users.

### Message type

1. **Informational** (`info`)
   - To provide information to users, and don't interrupt any current actions
   - Does not require immediate action and can be dismissed by a user clicking the [X] or passively display until the display timer expires
   - Shows blue color on the background and uses the `info-circle` icon
2. **Success** (`success`)
   - To confirm a task is completed as expected or an action is successful.
   - Typically does not require further action and can be dismissed automatically or persist in a nonintrusive manner
   - Shows green color on the background and uses the `check` icon
3. **Warning** (`warning`)
   - To inform users that an action is undesirable
   - Often persists until users have taken action to dismiss the notification or taken steps to resolve the issue
   - Shows yellow color on background and uses the `exclamation-triangle` icon
4. **Error** (`error`)
   - To inform that an action hasn't happened as expected, usually something has failed and the user is expected to take action
   - Always persists until the user has taken steps to remedy the issue that triggered the notification
   - Shows red color on background and uses the `exclamation-circle` icon

### Inline banner

Inline Banners are task-oriented alerts that notify users of the status of an action or system. These alerts are contextual, appearing above or below main content areas, allowing users to address issues or to read messages quickly.

For where to place it, see Placement and links under Do's and don'ts.

### Toast

Toast notifications are short messages that appear in the top-right corner of the page and are automatically hidden after a certain amount of time. They provide live notifications, without interrupting the user experience or requiring an action to be taken. They slide in and out from the top right corner of the page.

Don't use this component directly for a toast. Instead, emit the `appEvent` to trigger its appearance. Publish the `appEvent` with the proper type and payload needed, using `AppEvents` and `getAppEvents()`.

```tsx
import { AppEvents } from '@grafana/data';
import { getAppEvents } from '@grafana/runtime';

const appEvents = getAppEvents();
appEvents.publish({
  type: AppEvents.alertSuccess.name,
  payload: [text + ': ' + resp.status + ' (' + resp.statusText + ')'],
});
```

Grafana renders the toast for you, as an elevated, dismissible `Alert`, when you publish the `appEvent`.

### Main elements

- Icon status: represents the importance of the message through the color and icon for each status.
- Alert title: should be explicit, clear and short, conveying the most important part of the information.
- Details: precise description for the notification, telling users what they need to do.
- Button and text links: actions related to the message. See Placement and links under Do's and don'ts for which notifications can contain them.
- Close icon: appears when the notification can be dismissed by the user.

### Content

**Title:** the main message of the alert. See Writing content under Do's and don'ts.

**Description:** Description copy is optional and should be used sparingly. Keep the description copy short and focused on the reason for the Alert and include possible solutions or paths forward to prevent users from being blocked.

**Content guidelines (how to write):** It is important to always use simple and concise language when crafting messaging for Alerts. Avoid using jargon or system errors in the content of the Alerts. Provide users with a path forward or possible solution. For more recommendations on writing, view the [UX writing guidelines](https://grafana.com/docs/writers-toolkit/write/style-guide/ux-writing/).

**Calls to action:** Alerts (Inline Alerts specifically) can contain calls to action (CTAs), especially if there is an action a user can take to remedy or correct the reason the Alert is being shown. For CTA labels, see Writing content under Do's and don'ts and Grafana's [UX Writing guidelines](https://grafana.com/docs/writers-toolkit/write/style-guide/ux-writing/).

## Accessibility

`Alert` handles:

- **Role:** `error` and `warning` alerts get `role="alert"`, and `info` and `success` alerts get `role="status"`. Pass `role` to override it.
- **Name:** the alert's accessible name is its `title`. Pass `aria-label` to override it.
- **Close button:** the close icon button has the label "Close alert".

You provide:

- A `title` that makes sense on its own, because screen readers use it to name the alert.
- The right `severity`. `role="alert"` is announced as soon as the alert appears, so keep `error` and `warning` for messages that need that attention.
