Scopes API Reference

A client-oriented reference for scope.grafana.app/v0alpha1 — the Kubernetes-style API behind Grafana's Scopes feature. Covers CRUD endpoints, payload shapes, and the intended end-to-end workflow for generating scope hierarchies, independent of any particular calling application.

group: scope.grafana.app version: v0alpha1 stage: experimental

Overview

The Scopes API models a navigable hierarchy that end users select from to filter and navigate a Grafana instance — a "hat" a user puts on (e.g. a team, a service, a cluster) that narrows what they see. The hierarchy is built from two kinds working together:

  • ScopeNode — the tree structure itself (containers and leaves).
  • Scope — the actual filterable unit a leaf node links to, carrying the label filters that get applied once selected.

A third kind, ScopeNavigation, attaches dashboard/page links to a selected scope, grouped into folders in the navigation UI. A fourth, ScopeDashboardBinding, is an older flat dashboard-link mechanism that ScopeNavigation has superseded — included here for completeness since it's still a live, separate collection.

This is a real, live, CRUD-capable REST API — not a config file loaded once at startup. Every write in this document was exercised against a running Grafana instance before being documented; see Stability & caveats for exactly what was and wasn't verified this way.

Resource model

A typical generated hierarchy: containers from the root down to a service, a leaf node per filterable unit (here, a cluster), and navigation links hanging off the scope that leaf links to.

  root --> team
  team --> svc
  svc --> leaf
  leaf -- linkId --> scope
  scope -. "spec.scope" .-> nav1
  scope -. "spec.scope" .-> nav2

Containers exist purely to organize the tree — they have no filters of their own. Only leaf nodes link to a Scope, and only once selected does that Scope's filters take effect.

Base path & auth

All endpoints below are relative to:

apis/scope.grafana.app/v0alpha1/namespaces/{namespace}/{collection}
  • {namespace} — the stack/org namespace (e.g. default for a single-tenant instance; a Cloud stack namespace like stacks-<id> in a multi-tenant deployment).
  • {collection} — one of scopes, scopenodes, scopenavigations, scopedashboardbindings.

Authentication is whatever your Grafana instance normally requires for its HTTP API (session cookie, API key, or service account bearer token) — nothing scope-specific. This is an embedded Grafana App Platform API group, served in-process alongside the other built-in groups (dashboard.grafana.app, folder.grafana.app, etc.) — it does not require any cross-cluster aggregation setup to reach.

CRUD endpoints

Standard Kubernetes-style REST semantics throughout: GET on the collection lists, GET on an item name fetches one, POST to the collection creates, PUT/PATCH on an item name updates, DELETE on an item name removes it. There is no native upsert verb — see Upsert pattern.

Payload shape:

{
  "apiVersion": "scope.grafana.app/v0alpha1",
  "kind": "Scope",
  "metadata": {
    "name": "scope-checkout-us-east"
  },
  "spec": {
    "title": "us-east",
    "filters": [
      { "key": "cluster", "operator": "equals", "value": "us-east" },
      { "key": "service_name", "operator": "equals", "value": "checkout" }
    ],
    "defaultPath": ["svc-checkout", "team-platform", "root"]
  }
}
  • spec.title — display title shown in the scope picker.
  • spec.filters — the label filters applied once this scope is selected. See Filter model.
  • spec.defaultPath — optional. Direct-parent-to-root list of ScopeNode names (i.e. the linking leaf node's own ancestors, not including the leaf itself). Drives which tree path auto-expands when this scope is selected from elsewhere. Order confirmed by construction against a live tree; the auto-expand UI behavior itself was not independently re-verified.

Leaf node (links to a Scope):

{
  "apiVersion": "scope.grafana.app/v0alpha1",
  "kind": "ScopeNode",
  "metadata": { "name": "svc-checkout-cluster-us-east" },
  "spec": {
    "parentName": "svc-checkout",
    "nodeType": "leaf",
    "title": "us-east",
    "linkType": "scope",
    "linkId": "scope-checkout-us-east"
  }
}
  • spec.parentName — the parent node's name. An empty string marks a root node (no parent). Confirmed live: a node created with parentName: "" is correctly treated as a tree root by the find/scope_node_children query below, and is simply omitted (zero-value) from the object you read back rather than rejected.
  • spec.nodeType — container (pure hierarchy, no linkId) or leaf (links to a Scope).
  • spec.linkType / spec.linkId — only set on leaves; linkType is currently always "scope", linkId is the target Scope's metadata.name.
  • spec.subTitle, spec.description — optional, not covered by live testing for this document but present in the type definitions.
  • spec.disableMultiSelect — boolean, defaults to false in server responses even when omitted on write.
  • spec.redirectPath — optional string; jumps straight to a URL when this node is selected, bypassing normal scope selection. Not exercised for this document.

Create (spec only):

POST /scopenavigations
{
  "apiVersion": "scope.grafana.app/v0alpha1",
  "kind": "ScopeNavigation",
  "metadata": { "name": "scope-checkout-us-east-nav-overview" },
  "spec": {
    "url": "/d/abc123",
    "scope": "scope-checkout-us-east"
  }
}
The spec write above does not set status. Title and folder grouping live in status, which is a separate subresource — write it with a second request, carrying forward the resourceVersion the first write returned: 
PUT /scopenavigations/scope-checkout-us-east-nav-overview/status
{
  "apiVersion": "scope.grafana.app/v0alpha1",
  "kind": "ScopeNavigation",
  "metadata": {
    "name": "scope-checkout-us-east-nav-overview",
    "resourceVersion": "<resourceVersion from the create response>"
  },
  "spec": {
    "url": "/d/abc123",
    "scope": "scope-checkout-us-east"
  },
  "status": {
    "title": "Checkout overview",
    "groups": ["Dashboards"]
  }
}
  • spec.url — a raw path (e.g. /d/{dashboardUid}), not a typed resource reference. Anything the frontend can navigate to works.
  • spec.scope — the Scope this navigation entry belongs to.
  • status.title — display title for the navigation entry.
  • status.groups — list of folder names the entry is filed under in the navigation drawer. Confirmed live: setting groups: ["Dashboards"] files the entry under a "Dashboards" folder instead of showing it flat at the top level.
Writing to a status subresource directly from a client is unusual for Kubernetes-style APIs — status is normally controller-written. For ScopeNavigation there's no reconciler populating it, so a direct client write is the only way it gets set. Treat this as this API's actual contract, not a workaround.

ScopeDashboardBinding legacy

An older, flatter alternative to ScopeNavigation — a direct dashboard ↔ scope pair with no grouping or nested sub-scope support. Same collection shape (/scopedashboardbindings, full CRUD, a status subresource with dashboardTitle and groups). Not exercised for this document — ScopeNavigation is the actively-developed mechanism and the one to use for new integrations.

Filter model

Each entry in Scope.spec.filters:

{
  "key": "cluster",
  "operator": "equals",
  "value": "us-east",
  "values": ["us-east", "us-west"]
}
  • key — a literal label/column name (e.g. cluster, service_name, team) — not a dashboard template variable name. See How filters reach consumers.
  • value — single-value operators' operand.
  • values — multi-value operators' operand (one-of / not-one-of).
  • operator — one of the six below.
OperatorMatcher equivalent
equals=
not-equals!=
regex-match=~
regex-not-match!~
one-ofmulti-value match (values)
not-one-ofmulti-value exclusion (values)

This mapping (sourced from @grafana/data's scopeFilterOperatorMap) is what a Prometheus/Loki-style consumer resolves each operator to. It's informative for constructing filters correctly, even though the Scopes API itself has no opinion on how a given datasource applies them.

Note the ~15 minute cache observed on find/scope_navigations in practice — a navigation entry written moments ago may not appear immediately in this endpoint's response. Don't mistake that lag for a write failure.

Upsert pattern

There's no native "create or update" verb. The idempotent pattern that works, verified live end to end (including re-running it against objects that already existed):

  1. GET {collection}/{name}.
  2. If 200: PUT {collection}/{name} with the new desired spec, carrying forward metadata.resourceVersion from the GET response. A PUT without the current resourceVersion is rejected.
  3. If 404: POST {collection} to create it.
  4. Any other error status: surface it — don't treat it as "doesn't exist".

A no-op update (identical content to what's already stored) was observed to return the same resourceVersion rather than erroring or bumping it — safe to re-run unconditionally for idempotent generation.

End-to-end workflow

The generic recipe for generating a scope hierarchy from some external source of truth (a service catalog, an inventory system, anything), independent of what that source is.

  1. Pick a deterministic naming scheme. metadata.name is the primary key across every collection here (RFC 1123: lowercase alphanumeric and hyphens). Deriving names deterministically from your source data (rather than generating random IDs) is what makes the whole pipeline idempotent — see Upsert pattern.
  2. Create container ScopeNodes top-down. Start with one or more roots (parentName: ""), then each level referencing its parent's name. Order matters for clarity but wasn't observed to matter for correctness — the API accepted nodes referencing not-yet-created parents without error in testing, though creating top-down is the safer assumption to build on.
  3. Create the Scope objects that your leaf nodes will link to — one per actual filterable unit, with its filters and (if useful) defaultPath.
  4. Create the leaf ScopeNodes, each with nodeType: "leaf", linkType: "scope", and linkId pointing at the Scope from step 3.
  5. Create ScopeNavigation entries per scope — one per dashboard/page you want surfaced when that scope is selected — then follow up with the /status write for title and folder grouping.
  6. Re-run the whole pipeline on a schedule or on source-data change, relying on the upsert pattern rather than tracking a diff yourself.

Deletion

DELETE {collection}/{name} per object. No cascade was observed — deleting a parent ScopeNode does not delete its children, and nothing was observed enforcing referential integrity on delete (deleting a Scope that a ScopeNode still links to was not tested against a blocking constraint).

Since generated names are deterministic (see End-to-end workflow), bulk cleanup doesn't need to walk the tree at all: list each collection, delete anything matching your naming prefix, done. This also cleans up orphans left behind by a partial or failed generation run, which a tree-walk would miss. Delete scopenavigations and scopes before scopenodes as a defensive ordering (children-ish before parents-ish) — not confirmed to be required by the server, but cheap to do regardless.

How filters reach consumers

Worth understanding even though it's downstream of this API: a selected scope's filters reach query execution two ways, and neither is tied to a specific dashboard variable name:

  • Raw passthrough — the full Scope[] (filters included) is attached directly to the outgoing data query request. A datasource plugin that's scope-aware can read it and build its own matchers.
  • Ad-hoc filter merge — each selected scope's filters are converted to ad-hoc filter entries and merged into a dashboard's existing ad-hoc-filters variable, if one is present.

Practically: a scope's filters apply automatically to any datasource that already reads raw scope filters off the request, with zero dashboard-side setup. For datasources that don't, the target dashboard needs an ad-hoc-filters variable bound to a datasource that recognizes the filter's key as a real label/column — without one, nothing on the dashboard visibly reflects the filter even though it may still be silently applied at the datasource level.

Stability & caveats

  • API stage: v0alpha1, explicitly experimental. No stability guarantees — field names and behavior can change.
  • Deployment-dependent availability: this API group is served by Grafana's embedded App Platform layer. It's been observed present in a build that also links Grafana Enterprise; its availability in a plain OSS build was not independently confirmed for this document.
  • scopeFilters / useScopesNavigationEndpoint feature toggles: these govern whether Grafana's own UI surfaces scope selection and the navigation drawer to end users. They do not gate the REST API itself — a client can read and write scope objects via the API regardless, though with the toggles off, nothing in the UI will reflect what you've written.
  • Verification basis for this document: endpoints and payload shapes marked verified were exercised directly against a running instance (create, read, update-with-resourceVersion, delete, and the two find/* endpoints marked ✓ above). Everything else (PATCH, ScopeDashboardBinding, find/default_scope, redirectPath, disableMultiSelect's effect) is sourced from the API's type definitions and OpenAPI schema, not independently exercised.
